# План: перевод авторитета с клиента на сервер (Trust Refactor)

> Таск для следующего агента. Цель: мод станет публичным, поэтому нельзя больше
> доверять клиенту правила игры. Сервер должен стать авторитетным: держать
> собственную копию состояния каждой партии, валидировать каждый ход и
> отклонять нелегальные/не-в-свой-ход/подставные действия. Работаем в текущей
> ветке. Читать вместе с `ARCHITECTURE.md` (особенно §2, §5, §8.6, §9) и
> `server/README.md`.

---

## 0. Самое важное — почему всё устроено так (читать ПЕРВЫМ)

Транспорт **асимметричен**, и это определяет весь дизайн:

- **Downlink (ответ сервера) = размеры PNG = ровно 2 маленьких целых.** Каждое
  значение ≤ ~99–128 px, иначе округление от UI-scale его испортит. Через ответ
  НЕЛЬЗЯ вернуть доску, полное состояние или секрет. (`ARCHITECTURE §2`, §5.)
- **Uplink (URL query-параметры запроса) = НЕ ограничен.** На сервер можно слать
  сколько угодно данных.

Из-за узкого downlink авторы сделали сервер «тупым релеем ходов», а клиента —
авторитетом (`server/README.md`: *"Game rules live entirely on the client. The
server never validates a move — it just relays them in order. Fine for a friendly
game; do not treat it as cheat-proof."*).

**Главный вывод для рефактора:** чтобы сделать сервер авторитетным, НЕ нужно
менять downlink и НЕ нужно возвращать состояние вниз. Нужно:

1. Сервер держит **собственную авторитетную копию состояния** каждой партии и
   **валидирует каждый ход** серверным движком правил, ОТКЛОНЯЯ нелегальные.
   Отказ кодируется теми же 2 целыми (сигнал `(9,9)` уже существует).
2. Появляется **привязка вызывающего к месту (seat)** через
   **клиент-генерируемый секрет-токен**, который течёт ТОЛЬКО вверх (uplink
   неограничен → downlink-ограничение не мешает). Сейчас идентичности нет вообще:
   кто угодно, знающий 4-значный `code`, может слать `/api/move` за любого игрока.

Честный оппонент по-прежнему реконструирует доску из `/api/poll` — но теперь
сервер отдаёт туда только уже-провалидированные ходы. Читерский клиент, пославший
нелегальный ход, получит код отказа, ход в лог не попадёт, оппонент его не увидит.
Калибровка, FIFO-очередь, suspectDecode, рендер и драг — не трогаются.

## 1. Модель угроз (что именно чиним)

Сейчас модифицированный клиент может:

- **T1 — Нелегальные ходы.** Телепорт шашки, ход чужой фигурой, X в занятую
  клетку, игнор шаха в шахматах. Честный оппонент слепо реплеит присланный ход
  (`applyHop` / `makeMove` / `place`) — сервер ничего не проверяет.
- **T2 — Ход не в свой ход / за оппонента.** Нет проверки, чей сейчас ход, и нет
  идентичности игрока: любой со `code` шлёт `move` за любую сторону.
- **T3 — (Durak, Stage 2) чтение чужих рук.** Дизайн «worker-раздатчик» из
  `durak_plan.md` уже частично закрывает это, но остаётся дыра: без auth можно
  дёрнуть чужой `/api/ddraw` и узнать чужие карты (`ARCHITECTURE §8.6`).

Шашки / шахматы / крестики — игры с полной информацией → угрозы только **T1+T2**.
Durak добавляет **T3**.

**Что НЕ меняем:**
- Оффлайн-vs-бот (`session.bot`): сеть не вызывается, авторитет не нужен, ветки
  бота остаются как есть.
- Калибровку `/api/probe`, swap/scale, `suspectDecode`, FIFO `reqQueue`.
- Схему рендера, слайдов, drag-and-drop (`ARCHITECTURE §6, §7`).
- Downlink-формат (2 int). Добавляются только новые значения ОТКАЗА.

## 2. Целевая архитектура (после рефактора)

```
Клиент (mg_games / mg_durak):              Worker (авторитет, один Durable Object):
  локальные правила = ПРЕДИКТОР/UI           авторитетная копия state/turn per lobby
    (мгновенный отклик + подсветки)          валидирует КАЖДЫЙ /api/move движком правил
  свой ход → move{from,to,end,tok}           tok → seat, enforce «чей сейчас ход»
  poll реплеит валидированные ходы           illegal / out-of-turn / bad-tok → (9,x)
  отказ (9,x) → откат предсказания + ресинк   poll отдаёт ТОЛЬКО принятые ходы
  бот/оффлайн — без изменений
```

Всё состояние живёт в одном Durable Object («hub») — он strongly-consistent, что
идеально для авторитетной копии (нет KV-лага между игроками, `ARCHITECTURE §5`).

## 3. Секрет-токен места (фундамент, закрывает T2 и T3)

Токен ходит **только вверх** (в query), поэтому 2-int downlink не мешает.

Механика:
- Клиент при старте партии генерирует `tok` — длинная случайная строка (высокая
  энтропия). Хранится в памяти сессии (в `session.tok`), никогда не отображается
  в UI и никогда не приходит в ответе.
- **`/api/create?game=G&tok=<tok>`** → сервер создаёт лобби, seat 0 (host),
  `seats[0] = { tok }`. Ответ прежний `(CODE_HI, CODE_LO+1)`.
- **`/api/join?code=C&tok=<tok>`** → сервер занимает seat 1, `seats[1] = { tok }`.
  Ответ прежний `(G,1)` / `(20,1)` missing / `(21,1)` full. Место уже занято
  другим tok → `full`.
- **`/api/quick?game=G&tok=<tok>`** → роль (host/joiner) сервер уже определяет
  сам; пишет tok в соответствующий seat. Ответ прежний (роль во флаге `+100`).
- **`/api/move` / `/api/poll` / `/api/reset` / `/api/cancel`** — добавляют
  `&tok=<tok>`. Сервер по tok находит seat в лобби; tok не совпал ни с одним
  seat → отказ `(9,3)` bad-token.

Свойства безопасности:
- Чужой tok никогда не уходит вниз и случаен → подделать/угадать нельзя.
- Первый занявший место «застолбил» его своим tok.
- Это ровно «accepted trust level» из `durak_plan §2`, но усиленный: без tok
  нельзя действовать за место.

`poll` можно оставить БЕЗ обязательного tok (он только читает публичный лог), но
для единообразия и защиты от подглядывания в приватные каналы Durak — tok
обязателен на `dact`/`ddraw` (см. §7). Для 2-игроковых игр `poll` публичен и tok
на нём не критичен; решить по вкусу, но `move` — строго с tok.

## 4. Единый источник правил (чтобы сервер и клиент не разъехались)

Проблема: после рефактора правила нужны И на клиенте (предиктор + бот), И на
сервере (авторитет), в ДВУХ рантаймах (Panorama JS vs Cloudflare Worker ESM).
Дублирование кода = риск десинка на публичном моде (клиент считает ход легальным,
сервер — нет, или наоборот).

Хорошая новость: pure-секции уже написаны UI-free и уже слайсятся тестами
(`mg_rules_test.js`, `mg_chess_test.js`, `mg_durak_test.js`, `mg_server_test.js`).
То есть чистые правила уже отделены от рендера — их надо лишь физически вынести в
общие файлы.

### Путь A (рекомендуемый) — single source of truth + build-шаг

- Создать `rules/` (обычный JS, вешает функции на общий объект, БЕЗ `$`, `MG`,
  `export`):
  - `rules/checkers.js` — `initialBoard, simpleMoves, captureMoves, applyHop,
    legalSequences, hasAnyMove, anyCaptureFor, colorOf, ...` (перенос из
    `mg_games.js`).
  - `rules/ttt.js` — `tttWinner, tttFull, TTT_LINES, ...`.
  - `rules/chess.js` — `initialChessBoard, initialChessState, makeMove,
    legalMoves, pseudoMoves, inCheck, chessResult, ...`.
  - `rules/durak.js` — вся секция `// ── durak: pure rules ──` из `mg_durak.js`.
- Клиент: `panorama/layout/base_hud.xml` `<include>`-ит `rules/*.js` ПЕРЕД
  `mg_games.js` / `mg_durak.js`. Порядок: `mg_net → rules/* → mg_games →
  mg_durak → mg_ui`. Правила вешаются на `$.MG.Rules` (guard `if (MG.Rules) return`).
  Контроллеры используют `MG.Rules.*` вместо локальных копий.
- Сервер: билд `tools/build_worker.js` конкатенирует `rules/*.js` +
  `server/worker.core.js` → генерит деплой-артефакт `server/worker.js`. Правила —
  физически одни и те же байты на обеих сторонах.
- `server/README.md`: перед `npx wrangler deploy` запускать `node tools/build_worker.js`.

### Путь B (fallback, если build-шаг нежелателен)

- Скопировать pure-секции в `worker.js` вручную и покрыть server-side тестами,
  ПЛЮС обязательный parity-тест (§8): на N случайных позиций клиентский и
  серверный движки дают одинаковый `legalMoves`. Дешевле сейчас, дороже в
  поддержке (два места правды).

**По умолчанию в этом плане — Путь A.** Если мейнтейнер против build-шага, взять
Путь B, но parity-тест обязателен в обоих случаях.

> ⚠️ Осторожно со слайс-маркерами тестов: `mg_durak_test.js` режет секцию по
> строкам-баннерам `// ── durak: pure rules` и `// ── durak controller`. При
> переносе в `rules/durak.js` обновить тест (читать файл `rules/durak.js` целиком
> вместо слайса), либо сохранить баннеры. Не ломать существующие харнессы.

## 5. Серверное состояние и валидаторы (ядро, закрывает T1)

Расширить структуру лобби в worker (`worker.core.js` при Пути A):

```js
lobby = {
  game, players, moves: [], pub, t,          // как сейчас
  seats: [ { tok }, { tok } ],                // NEW: идентичность мест (§3)
  turn: 0,                                     // NEW: индекс места, чей сейчас ход
  state: <game-specific>                       // NEW: авторитетная доска/состояние
}
```

`state` инициализируется на `create` / `quick` / `reset` по `game`:
- **checkers (id 1):** `{ board: initialBoard(), turn: WHITE, chainSq: -1 }`
  (`chainSq` = клетка фигуры в середине незавершённого мультиджампа, иначе -1).
- **ttt (id 2):** `{ board: Array(9).fill(0), turn: X }`.
- **chess (id 4):** `{ board: initialChessBoard(), cst: initialChessState(),
  turn: +1 }`.
- Соответствие seat↔сторона фиксированное (как в клиенте): host = seat 0 =
  WHITE / X / +1 (ходит первым); joiner = seat 1 = BLACK / O / −1.

Новый серверный путь `/api/move?code=C&from=F&to=T&end=E&tok=<tok>`:
1. Найти лобби; нет → `(9,9)`.
2. `tok → seat`; не найден среди `seats` → `(9,3)` bad-token.
3. Проверить право хода СЕЙЧАС:
   - checkers: если `chainSq >= 0`, ходить может только владелец `chainSq` и
     только этой фигурой (продолжение цепочки капчи); иначе требуется
     `seatSide(seat) === state.turn`.
   - ttt / chess: `seatSide(seat) === state.turn`.
   - Иначе → `(9,1)` not-your-turn.
4. Сгенерировать легальные ходы серверным движком и проверить, что `{from,to}`
   среди них:
   - checkers: учесть форс-капчу (`anyCaptureFor`), флайинг-кингов, мультиджамп;
     `end` должен соответствовать (end=1 только если после хода нет продолжения
     капчи или было промо).
   - chess: `legalMoves(board, cst, side)` — сюда уже входит фильтр самошаха,
     кастлинг, энпассан; промо всегда в ферзя (MVP).
   - ttt: `from ∈ 0..8`, клетка пуста, `to === 9` (фиксированный маркер).
   - Нелегально → `(9,2)` illegal-move.
5. Применить к серверной доске (`applyHop` / `makeMove` / `place`), обновить
   `chainSq` / `turn`, зафиксировать корректный `end`. Затем
   `moves.push({ f, t, e })`, вернуть `(1,1)`.

`/api/poll?code=C&since=S` — семантика без изменений: отдаёт `moves[since]`
(теперь там только валидированные ходы). Клиентский диапазон-чек + `validate`
остаются как есть.

**Коды отказа (все влезают в 2 int, обратносовместимо с текущим `(9,9)`):**

| Ответ | Значение |
|---|---|
| `(9,9)` | нет лобби / уничтожено (как сейчас) |
| `(9,1)` | не твой ход |
| `(9,2)` | нелегальный ход |
| `(9,3)` | плохой/чужой токен |

Клиент может показать разное сообщение, но по умолчанию любой `w === 9` в ответе
на `move` трактует как «отклонено → откат предсказания + ресинк» (§6).

## 6. Изменения на клиенте

### `panorama/scripts/mg_net.js`
- Добавить `MG.Session = { newToken: function(){ /* высокоэнтропийная строка */ } }`.
- Во все `MG.Api.create/quick/join/move/poll/reset/cancel` пробрасывать `tok`
  (параметр функции или из общего `session`). Токен кладётся в `params`.
- Расширить декод ответа `move`: сейчас `cb(w < 9)`. Сделать
  `cb({ ok, reason })`, где `reason ∈ { "turn"(9,1), "illegal"(9,2),
  "token"(9,3), "gone"(9,9) }`. Обратная совместимость: `ok === (w < 9)`.

### `panorama/scripts/mg_ui.js`
- Генерировать `tok = MG.Session.newToken()` ОДИН раз на партию в `startCreate`,
  `startQuickMatch`, `doJoin`; класть в `session` рядом с `code/isHost/bot`.
- Передавать `tok` в `renderGame(...)` → в `MG.Games.mount(...)`.

### `panorama/scripts/mg_games.js` (checkers / ttt / chess контроллеры)
- Локальные правила остаются как **предиктор** (мгновенный UI-отклик, подсветки,
  анимация) — это НЕ авторитет, но UX.
- В `sendHops` / `sendMove` / `sendChessMove` прокидывать `session.tok`.
- **Обработка отказа сервера:** если `move` вернул `!ok` (любой `(9,x)`):
  - Откатить локально предсказанный ход (простейший вариант — перечитать
    авторитетную последовательность: сбросить `appliedSeq`-догон через poll и
    перестроить доску; либо хранить снапшот доски перед предсказанием и
    восстановить его).
  - Показать `status("Move rejected — resyncing…")` и вернуться в режим
    ожидания/поллинга. Честный клиент так не застрянет при случайном десинке;
    читер просто не сможет продвинуть нелегальный ход.
- Переключить движок на `MG.Rules.*` (из §4). Локальные дубли правил либо удалить,
  либо оставить тонкими ре-экспортами, чтобы не ломать `mg_rules_test.js` /
  `mg_chess_test.js` (обновить тесты на новый источник — предпочтительно).
- Бот/оффлайн ветки (`session.bot`) — НЕ трогаем.

### Durak `mg_durak.js`
- Пока Stage 1 (оффлайн) — без изменений. Онлайн — см. §7.

## 7. Durak Stage 2 — сразу проектировать server-authoritative + tok

`durak_plan.md` уже закладывает worker-раздатчика; этот рефактор делает его
безопасным:
- `/api/start`, `/api/dact`, `/api/dlog`, `/api/ddraw` — **все требуют
  `&tok=<tok>` и seat-привязку**. Это закрывает T3 (нельзя дёрнуть чужой `ddraw`).
- Сервер владеет колодой / руками / сидом: `newGame(numPlayers, seed)` из
  `rules/durak.js`. Валидирует каждое `dact` теми же
  `canAttackWith` / `canDefendPair` / `legalDefends` / `applyAttack` /
  `applyDefend` / `endBout`.
- Публичный лог `dlog` отдаёт события `TRUMP / PLAY / COVER / TAKE / DONE / DRAW`
  (индексируемый лог по образцу `moves[]`); приватные идентичности карт места —
  ТОЛЬКО через `ddraw` со своим tok.
- Клиенты восстанавливают стол/козырь/чей ход/роли/размер колоды/число карт у
  всех из публичного лога; свои карты — из `ddraw`.
- Онлайновые кнопки Durak (`onlineReady` в `mg_ui.js`) включаем только когда
  Stage 2 готов и протестирован.

Так Durak Stage 2 становится частью этого же trust-рефактора, а не отдельной
незащищённой историей.

## 9. Порядок работ (по коммитам/шагам)

1. **Rules extraction (§4).** Вынести pure-секции в `rules/*.js`; переключить
   `<include>` и контроллеры на `MG.Rules.*`; обновить существующие тесты на
   новый источник. Прогон — зелёные, поведение НЕ изменилось.
2. **Build step (§4, Путь A).** `tools/build_worker.js` + правка
   `server/README.md`; сгенерить `worker.js` без логических изменений — тесты
   зелёные.
3. **Tokens (§3).** `seats`/`tok` в worker + проброс в `MG.Api` / `mg_ui`;
   `move`/`poll` с tok; отказ `(9,3)`. Тесты на tok-поток.
4. **Server state + validation (§5).** Инициализация `state`, серверные

5. **Client resync (§6).** Откат предсказания при отказе + сообщения. (verified:

## 10. Риски и заметки

- **Обратная совместимость лобби:** старые лобби без `seats`/`state` эфемерны
  (свип 30 мин, `maybeSweep`). На всякий случай трактовать отсутствие `state` как
  «инициализировать по game». Деплой worker атомарный.
- **Мультиджамп + `end`-флаг** в шашках — самая тонкая серверная валидация;
  тестировать отдельно (несколько цепочек, промо в середине цепочки завершает ход).
- **Downlink остаётся 2 int** — расширять ответ НЕ требуется, только больше
  значений отказа. Калибровку/`suspectDecode` не трогаем.
- **Токен только в uplink** — не логировать его в `debug()` в открытую (или
  маскировать), чтобы не утёк в dev-консоль.
- **Ничего из §5/§6 в части СЕТЕВОГО поведения в игре нельзя подтвердить из
  шелла** — только репак VPK мейнтейнером. Node-тесты подтверждают правила,
  протокол и tok-логику.
- **Не коммитить/не пушить** без явного согласия мейнтейнера.
